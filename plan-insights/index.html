Making plan changes explainable

the short version

The original problem was not a lack of data. It was the amount of work required to turn that data into a defensible explanation.

Planners repeatedly downloaded files, rebuilt pivots, searched logs, and assembled answers by hand. I designed a guided comparison flow that made analytical scope explicit, showed visual evidence before generated interpretation, and kept supporting records close enough to verify the answer.

The use case also exposed missing interaction primitives in the shared AI canvas. I helped turn those product needs into reusable controls, charts, grids, events, citations, and template patterns for later experiences.

the problem

Analysts had access to snapshots, sessions, planning records, and logs, but the path from a stakeholder question to an explanation was fragmented and difficult to repeat.

task-flow redesign

I centered the product on the analytical question instead of exposing the files and backend systems needed to answer it.

Before

  1. Interpret the stakeholder question.
  2. Find datasets and snapshots.
  3. Download large files.
  4. Build pivots manually.
  5. Search logs and records.
  6. Assemble the explanation.

After

  1. Choose the analysis intent.
  2. Select baseline and comparison.
  3. Inspect the visual change.
  4. Narrow the scope with filters.
  5. Read the synchronized explanation.
  6. Trace records and likely drivers.

design principles

Make analytical scope explicit.

Intent, snapshots, sessions, dates, and filters should be visible before the system produces an answer.

Show evidence before interpretation.

Visual changes and supporting data establish trust before a generated narrative asks the user to believe it.

Keep the explanation synchronized.

When users narrow the chart or pivot, the narrative should reflect the same visible scope.

Preserve a path to verification.

Charts, pivots, citations, and traces should connect the summary back to records and likely drivers.

coded prototyping

evaluation and iteration

Feedback became specific design and implementation changes rather than a general statement that the product needed improvement.

Planning-SME feedback

Users trusted charts before generated text.

I moved to a visual-first hierarchy and made chart types configurable.

Pilot and production feedback

Filters disappeared between views.

I preserved state across charts, pivots, and summaries.

User enhancement request

The narrative did not reflect narrowed scope.

Visible filters were sent with insight requests and regeneration.

Demo observation

The page felt slow while users waited.

I separated data, visual, and insight loading paths.

Early-use feedback

Users could trigger duplicate requests.

I added a disabled Analyze state and clearer progress behavior.

Co-design and bug reports

Dense dropdowns slowed selection.

I improved filtering, defaults, placeholders, and width.

platform contribution

The first use case exposed interaction patterns the canvas did not yet provide. I promoted those product needs into shared React widgets and event contracts for later analytics experiences.

Combo-box widget

Typed selection, filtering, defaults, sizing, and change events.

Interactive graph

Configurable chart types, series, labels, and click callbacks.

Pivot grid

Grouping, aggregation, filtering, side panels, and detail events.

Citation and trace flow

Connections from summaries and visual selections to supporting records.

Event coordination

Decoupled chart, grid, selection, and message behavior.

Template configuration

Dataset variation without cloning the full experience.

impact and reflection

The result created direct user value and future delivery leverage for the shared canvas.

  • Less preparation Supported questions moved from repeated exports and spreadsheet pivots toward on-demand comparison.
  • ~20 hours/month Business-review estimate of monthly time savings, presented as a stakeholder estimate rather than measured product telemetry.
  • Broader visibility The experience reached planning demos, leadership reviews, and wider adoption conversations.
  • Reusable foundation The evolved flow later informed generic dataset comparison and additional canvas workflows.

What I learned

AI UX becomes trustworthy when scope, evidence, and verification are visible rather than hidden behind a fluent answer.

What I would improve

I would add structured task-based usability sessions and time-to-insight instrumentation earlier.

the takeaway

I can research the workflow, design the interaction, build the product, and strengthen the platform beneath it. That combination of user-centered judgment and implementation depth is the value I bring to UX engineering and design engineering roles.
