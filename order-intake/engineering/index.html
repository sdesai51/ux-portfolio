the technical problem

This page was less a dashboard than a coordination problem.

Filters defined the visible operational population. Row selection updated details, exception evidence, reservation history, and conversational context. Resolution added another layer of eligibility, prior-action state, approval, and results.

Any one of those pieces could work in isolation and still leave the workflow feeling unreliable if the state between them drifted.

My engineering goal was to make the frontend an explicit contract between business rules and what the user could safely see or do.

architecture

I separated the feature into layers with narrow responsibilities, then synchronized them through explicit state and event streams.

01 Routed feature shell

Owned the active mode, side navigation, page-level layout, deeplink input, and feature lifecycle.

02 Query services

Loaded demand populations, exceptions, reservation history, and remediation state through separate contracts.

03 Focused stores

Tracked filtered rows, selected rows, selected IDs, and remediated IDs without one page-wide mutable object.

04 Renderers

Built schema-driven grids, status cells, details, empty states, and the event-history visualization.

05 Action layer

Applied eligibility, constrained bulk selection, submitted remediation, and represented completed outcomes.

two modes, one foundation

Explicability and resolution shared data and context, but they did not share every rule. I resisted collapsing them into one generic workflow.

key engineering decisions

Schema evolution

Generate grid behavior from API data.

Dynamic columns, friendly labels, date formatting, links, and filters reduced coupling to frequently changing operational fields.

State coordination

Use focused stores rather than one page-wide object.

Selected rows, visible data, selected IDs, and remediated IDs could evolve independently while remaining synchronized.

Bulk-action safety

Constrain actions to visible, eligible records.

A production refinement ensured filtered-out rows could not remain silently selected for remediation.

Workflow continuity

Preserve context across entry points.

Deeplinks, auto-scroll, and selected-demand state connected navigation, grids, details, history, and assistance.

Lifecycle semantics

Distinguish empty domain data from failure.

“No reservation history” became an understandable state rather than a generic error-shaped experience.

Assistant readiness

Wait for initialization before selecting context.

The page prevented race conditions between the routed feature and its conversational assistant.

how the implementation evolved

Foundation

Route, components, stores, and event history

Decomposed the early page into a shell, sidebar, grid, details area, services, state, and visualization renderer.

Live data

Operational APIs and dynamic columns

Moved from prototype data to evolving contracts while keeping the presentation layer adaptable.

Evidence

Exceptions, status, and conversational context

Added scannable status, quick filters, supporting records, and assistant activation.

Action

Resolution, eligibility, and results

Added a separate remediation workflow with disabled states and prior-action awareness.

UAT

Filtering and workflow alignment

Aligned fixability, intent, and planning filters across diagnostic and action modes.

Production

Selection, navigation, and domain states

Hardened filtered selection, auto-scroll, deeplinks, hidden fields, and empty-history behavior.

engineering takeaway

I built the interaction model and the frontend system required to keep it trustworthy. The most important technical choices were the ones that made scope, state, eligibility, and failure visible to the user.
